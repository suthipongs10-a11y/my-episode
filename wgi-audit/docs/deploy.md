# รันที่ไหนได้บ้าง

คำตอบสั้น: **รันบนเว็บได้** และมี 3 ทางที่ใช้ได้จริง กับ 1 ทางที่คนมักคิดว่าได้แต่ไม่ได้

ก่อนอื่น — **ตั้ง `DASHBOARD_PASSWORD` เสมอ** ถ้าจะให้เข้าถึงจากนอกเครื่อง
เซิร์ฟเวอร์จะ **ปฏิเสธการเปิด** ถ้า `WEB_HOST` ไม่ใช่ `127.0.0.1` แล้วยังไม่ตั้งรหัส
(`apps/web/src/auth.ts`) หน้านี้มีข้อมูลลูกค้าทุกราย และไม่มีอะไรกั้นนอกจากรหัสนี้

---

## เลือกทางไหนดี

| | ค่าใช้จ่าย | เหมาะกับ | ต้องทำอะไรเพิ่ม |
|---|---|---|---|
| **1. บนเครื่องตัวเอง** | 0 | ตอนนี้ · คุณคนเดียว | ไม่ต้อง |
| **2. Cloudflare Tunnel** | 0 | เปิดจากมือถือ / โน้ตบุ๊กที่ออฟฟิศลูกค้า | ติดตั้ง `cloudflared` |
| **3. VPS / container host** | ~150-250 ฿/เดือน | ใช้จริงจัง · ให้ลูกค้ากรอกฟอร์มเอง (M6) | Supabase + รหัสผ่าน |
| ~~4. Vercel / Netlify / Workers~~ | — | **ใช้ไม่ได้** | ดูเหตุผลท้ายไฟล์ |

**ตอนนี้แนะนำข้อ 1** จนกว่าจะมีลูกค้าประจำ แล้วค่อยขยับไปข้อ 3
ข้อ 2 ทำเมื่อไหร่ก็ได้ ใช้เวลา 10 นาที และไม่ต้องแก้โค้ด

## 1. บนเครื่องตัวเอง (ตอนนี้ใช้ได้เลย)

```bash
cd wgi-audit
pnpm install
pnpm dash          # http://127.0.0.1:4321
```

ข้อมูลเก็บใน PGlite ที่ `.data/dev` เป็นไฟล์บนเครื่อง ไม่ต้องมีฐานข้อมูลอะไรเลย
ไม่ต้องมีรหัสผ่านเพราะเข้าได้จากเครื่องนี้เท่านั้น

**ข้อจำกัด:** ปิดเครื่องแล้วเข้าไม่ได้ · ดูจากมือถือไม่ได้ · ข้อมูลอยู่เครื่องเดียว

---

## 2. Cloudflare Tunnel — อยู่บนเครื่องเหมือนเดิม แต่เข้าจากที่ไหนก็ได้

เหมาะมากถ้าอยากเปิดให้ลูกค้าดูจากจอที่ออฟฟิศเขา หรือเช็คงานจากมือถือ
โดยไม่ต้องย้ายอะไรขึ้น cloud และไม่ต้องเปิดพอร์ตที่เราเตอร์

```bash
# ครั้งเดียว
winget install Cloudflare.cloudflared      # หรือ brew install cloudflared

# ทุกครั้งที่จะเปิด — สองหน้าต่าง
pnpm dash
cloudflared tunnel --url http://127.0.0.1:4321
```

ได้ URL แบบ `https://xxx.trycloudflare.com` มาใช้ทันที

**ต้องตั้งรหัสผ่านด้วย** เพราะ URL นั้นใครก็เข้าได้ถ้ารู้:

```bash
# Windows PowerShell
$env:DASHBOARD_PASSWORD="ตั้งรหัสยาว ๆ"; $env:WEB_SECURE_COOKIE="1"; pnpm dash

# macOS / Linux
DASHBOARD_PASSWORD='ตั้งรหัสยาว ๆ' WEB_SECURE_COOKIE=1 pnpm dash
```

> อยากได้ชื่อโดเมนถาวรและหน้าล็อกอินของ Cloudflare เอง (Cloudflare Access)
> ต้องทำ named tunnel ซึ่งต้องมีโดเมนอยู่ใน Cloudflare — ฟรีเหมือนกัน แต่ตั้งค่านานกว่า

## 3. VPS หรือ container host — ทางที่ถูกต้องเมื่อใช้จริงจัง

ต้องเป็นที่ที่รัน **โปรเซสค้างไว้ได้ตลอด** เพราะ audit หนึ่งครั้งใช้เวลาเป็นนาที
ไม่ใช่ฟังก์ชันที่ตื่นมาแล้วตายไป

ที่ใช้ได้: **Render · Railway · Fly.io · Hetzner · DigitalOcean · Contabo**
ทุกเจ้ารับ Docker ได้ และ repo นี้มี `Dockerfile` ให้แล้ว

### ฐานข้อมูล — นี่คือ "เชื่อมกับอะไร"

PGlite เก็บเป็นไฟล์บนดิสก์ ซึ่งบน host พวกนี้**หายทุกครั้งที่ deploy**
ต้องย้ายไป Postgres จริง โค้ดรองรับอยู่แล้ว เปลี่ยนแค่ตัวแปรเดียว:

```bash
DATABASE_URL=postgresql://postgres:[password]@db.[ref].supabase.co:5432/postgres
```

**Supabase** free tier พอสำหรับงานช่วงแรก (สเปกเดิมก็เลือกตัวนี้)
ตอนเปิดครั้งแรกโค้ดจะสร้างตารางเองจาก `schema.sql` ไม่ต้อง migrate มือ

> ก่อน deploy จริง รันเทสต์กับฐานข้อมูลนั้นหนึ่งรอบ:
> `DATABASE_URL=... pnpm vitest run packages/core/src/db` ต้องผ่าน 25/25
> (เคยมีบั๊ก jsonb ที่ PGlite จับไม่ได้ — ดู Decision Log ใน STATUS.md)

### ตัวแปรที่ต้องตั้ง

| ตัวแปร | ค่า | จำเป็น |
|---|---|---|
| `DASHBOARD_PASSWORD` | รหัสยาว ๆ | **ใช่** — ไม่ตั้งแล้วเซิร์ฟเวอร์ไม่ยอมขึ้น |
| `DATABASE_URL` | Supabase / Postgres | **ใช่** — ไม่งั้นข้อมูลหายทุก deploy |
| `SESSION_SECRET` | สุ่มยาว ๆ | ควรตั้ง — ไม่งั้น session หลุดทุกครั้งที่ restart |
| `WEB_SECURE_COOKIE` | `1` | ใช่ ถ้าเป็น https |
| `WEB_TRUST_PROXY` | `1` | ใช่ ถ้ามี proxy ข้างหน้า (มีเกือบทุกเจ้า) |
| `HTTP_USER_AGENT` | ใส่โดเมนจริงของเรา | ควร — เจ้าของเว็บที่เราไป crawl ควรสืบกลับได้ |

API keys (`PSI_API_KEY`, `DFS_LOGIN`, …) ใส่เพิ่มเมื่อสมัครแล้ว
ไม่ใส่ก็ยังทำงานได้ แค่ได้ข้อมูลน้อยลง

### รันด้วย Docker

> **`Dockerfile` ยังไม่เคย build จริง** — เครื่องที่เขียนไม่มี Docker daemon
> สิ่งที่ตรวจแล้ว: ทุก path ที่ `COPY` มีอยู่จริง · `pnpm install --frozen-lockfile`
> ผ่าน · คำสั่ง healthcheck รันได้และคืน exit 0 กับเซิร์ฟเวอร์จริง
> สิ่งที่ยังไม่ได้ตรวจ: PGlite (WASM) ทำงานใน image นี้ไหม — ซึ่งไม่สำคัญถ้าใช้
> `DATABASE_URL` ตามที่แนะนำ · **build ครั้งแรกให้เผื่อเวลาแก้ไว้หน่อย**

```bash
docker build -t wgi-audit .
docker run -p 8080:8080 \
  -e DASHBOARD_PASSWORD='...' \
  -e SESSION_SECRET='...' \
  -e DATABASE_URL='postgresql://...' \
  -v wgi-cache:/app/.cache \
  wgi-audit
```

`-v wgi-cache:/app/.cache` ทำให้ cache อยู่ข้าม restart — ประหยัดเงินและ
ไม่ไปรบกวนเว็บคนอื่นซ้ำ ๆ

### ขนาดเครื่อง

RAM 512 MB พอ · 1 vCPU พอ · crawl ถูกจำกัดที่ 1 request/วินาที/โดเมนอยู่แล้ว
คอขวดคือเวลา ไม่ใช่ CPU

## 4. ทำไม Vercel / Netlify / Cloudflare Workers **ใช้ไม่ได้**

เขียนไว้ให้ชัด เพราะเป็นข้อที่คนคิดว่าได้บ่อยที่สุด

**เหตุผลหลัก — เวลา** audit หนึ่งครั้งใช้หลายนาที: crawl 150 หน้าที่
1 req/วินาที = 150 วินาทีเป็นอย่างต่ำ ยังไม่รวม PageSpeed ที่ครั้งละหลายสิบวินาที

| แพลตฟอร์ม | เวลาสูงสุดต่อ 1 request |
|---|---|
| Vercel Hobby | 60 วินาที |
| Vercel Pro | 300 วินาที |
| Netlify Functions | 10 วินาที |
| Cloudflare Workers | จำกัด CPU time ต่อ request |

**เหตุผลรอง — runtime** โค้ดนี้ใช้ `node:http`, `node:fs` (disk cache),
cheerio, และ PGlite (WASM) ซึ่ง edge runtime รันไม่ได้

**ถ้าจะใช้จริง ๆ** ต้องแยกเป็นสองส่วน: หน้าเว็บอยู่ Vercel · worker อยู่ VPS ·
ฐานข้อมูลอยู่ Supabase — ซับซ้อนขึ้นโดยไม่ได้อะไรเพิ่มในตอนนี้
**ไว้ค่อยทำตอน M6** ถ้าเว็บสาธารณะโตจนต้องแยกจริง

> Cloudflare ยังมีประโยชน์อยู่ — ใช้เป็น CDN/DNS หน้า VPS ได้ตามปกติ
> ที่ใช้ไม่ได้คือการเอา *ตัว audit* ไปรันบน Workers

## ยังไม่ได้ทำ (รู้ไว้ก่อนเปิดให้คนอื่นใช้)

- **บัญชีผู้ใช้มีเดียว** — รหัสเดียวใช้ร่วมกัน ไม่มีระบบหลายคน ไม่มี log ว่าใครทำอะไร
- **ยังไม่มี HTTPS ในตัว** — ต้องพึ่ง proxy ของ host หรือ Cloudflare
- **ลิงก์รายงานยังไม่มีแบบแชร์ให้ลูกค้าเปิดเอง** — ตอนนี้พิมพ์เป็น PDF แล้วส่งไป
  (ลิงก์แชร์อยู่ใน M6 และต้องคิดเรื่อง PDPA ด้วย — ดู `CLAUDE.md §8`)
- **ยังไม่มีการสำรองข้อมูล** — ถ้าใช้ Supabase เขามี backup ให้ระดับหนึ่ง
