## §0 สรุปสั้น

ระบบเดียว 8 หน้าจอ ฐานข้อมูล 11 ตาราง ทุกอย่างผูกกับ **"งาน" (Job)** เป็นแกนกลาง

สิ่งที่ระบบตอบได้ ซึ่งตอนนี้ตอบไม่ได้:

1. งานทั้งหมดตอนนี้อยู่สถานะไหน และงานไหน **ค้างเพราะเรา** งานไหน **ค้างเพราะลูกค้า**
2. งานนี้ **กำไรจริงเท่าไหร่** หลังหักค่าโฆษณาที่ปันส่วนลงไปแล้ว
3. เดือนนี้ยิงโฆษณาไปเท่าไหร่ ได้ลูกค้าทักมากี่คน ปิดได้กี่งาน **ต้นทุนต่อ 1 งาน** เท่าไหร่
4. โดเมน/โฮสติ้งของลูกค้าคนไหน **ใกล้หมดอายุ** ใน 30 วันข้างหน้า
5. ตอนนี้ **ค้างรับ** อยู่กี่บาท จากใครบ้าง

ข้อ 2 กับ 3 คือเหตุผลหลักที่ต้องเป็นระบบ ไม่ใช่ Excel — เพราะมันต้องเอาข้อมูลจาก
3 ที่ (งาน + ค่าใช้จ่าย + ค่าโฆษณาจากเพจ) มาชนกันอัตโนมัติ

## §1 ปัญหาจริงที่ต้องแก้ เรียงตามเงินที่เสียถ้าไม่แก้

**1. ไม่รู้กำไรจริง — เสียเงินมากที่สุด**
ราคา 990 เป็นราคาที่ไม่มีที่ว่างให้พลาด ค่าโฆษณาต่องานเพิ่มขึ้น 200 บาท
กำไรหายไป 25% ทันที ถ้าไม่บันทึกต้นทุนผูกกับงานเป็นราย ๆ จะไม่มีวันรู้ว่า
เดือนที่ยิงโฆษณาหนักคือเดือนที่ได้งานเยอะ หรือเดือนที่ทำฟรี

**2. งานค้างโดยไม่มีใครตาม**
งานเว็บราคาถูกค้างที่จุดเดียวเสมอ: **รอลูกค้าส่งข้อมูล/รูป/ข้อความ**
งานแบบนี้ไม่ตาย แต่ไม่จบ และไม่มีใครเห็นมันเพราะมันไม่ส่งเสียง
ระบบต้องนับอายุของสถานะ และดันงานที่ค้างเกิน 7 วันขึ้นมาให้เห็น

**3. ลืมต่ออายุโดเมน/โฮสติ้ง**
เว็บลูกค้าดับ = เสียชื่อ + เสียงานบอกต่อ + เสียรายได้ต่ออายุ
และรายได้ต่ออายุคือ **กำไรที่ดีที่สุดในโมเดลนี้** เพราะเก็บเงินได้โดยแทบ
ไม่มีต้นทุนเพิ่มและไม่ต้องจ่ายค่าโฆษณาเพื่อให้ได้มา (§6.4)

**4. ตอบลูกค้าเก่าไม่ได้**
"พี่ครับ เว็บผมล็อกอินยังไงนะ" — ถ้าคำตอบอยู่ในแชท LINE เมื่อ 8 เดือนก่อน
นั่นคือเวลาที่หายไปฟรีทุกครั้ง

## §2 หลักคิด — ทุกอย่างผูกกับ "งาน"

**Job คือหน่วยเดียวที่มีครบทั้ง ลูกค้า / สถานะ / เงินเข้า / เงินออก / เว็บที่ส่งมอบ**
ทุกตารางในระบบนี้มีไว้เพื่ออธิบายงานใดงานหนึ่ง หรือเพื่ออธิบายว่างานนั้นมาจากไหน

กฎเหล็ก 3 ข้อ ที่ถ้าไม่ทำ ระบบจะคำนวณกำไรไม่ได้เลย:

1. **ค่าใช้จ่ายทุกบาทต้องตอบได้ว่าเป็นของงานไหน** ถ้าตอบไม่ได้ ให้ลงเป็น
   ค่าใช้จ่ายรวม (`job_id` เป็น NULL) แล้วระบบจะปันส่วนให้เอง — แต่ต้องถูกบันทึก
2. **ลูกค้าที่ทักเข้ามาต้องถูกบันทึกทุกคน แม้จะไม่ปิดการขาย** ถ้าบันทึกเฉพาะ
   คนที่ซื้อ ตัวหารของ "อัตราปิดการขาย" จะหายไป และค่าโฆษณาจะดูถูกเกินจริง
3. **ค่าโฆษณาเป็นต้นทุนของงาน ไม่ใช่ค่าใช้จ่ายลอย ๆ** งานที่ปิดได้ต้องแบก
   ค่าโฆษณาของคนที่ทักมาแล้วไม่ซื้อด้วย นี่คือต้นทุนจริงของการได้ลูกค้า 1 คน

## §3 โครงสร้างข้อมูล — 11 ตาราง

โครงจริงอยู่ใน [`schema.sql`](schema.sql) ตารางนี้คือเหตุผลว่าแต่ละตัวมีไว้ทำไม

| ตาราง | เก็บอะไร | ทำไมต้องมี |
|---|---|---|
| `customers` | ชื่อ ชื่อร้าน เบอร์ LINE ID ลิงก์ FB ที่อยู่ เลขผู้เสียภาษี | ลูกค้า 1 คนอาจมีหลายงาน (เว็บ + แก้ + ต่ออายุ) แยกออกมาเพื่อดูมูลค่ารวมต่อคน |
| `leads` | คนที่ทักมา ช่องทาง แคมเปญที่พามา สถานะ เหตุผลที่ไม่ซื้อ | ตัวหารของอัตราปิดการขาย และเป็นสะพานเดียวที่เชื่อมค่าโฆษณาเข้ากับรายได้ |
| `jobs` | งาน 1 ชิ้น: แพ็กเกจ ราคาขาย สถานะ กำหนดส่ง จำนวนรอบแก้ | แกนกลางของทุกอย่าง |
| `job_tasks` | เช็กลิสต์ย่อยของงาน สร้างจาก template ตอนเปิดงาน | ทำให้ "งานเสร็จ 60%" เป็นตัวเลขจริง ไม่ใช่ความรู้สึก |
| `websites` | โดเมน URL ผู้ให้บริการ วันหมดอายุ ค่าต่ออายุ ที่อยู่ของรหัสผ่าน | หัวใจของหน้าต่ออายุ (§5.7) และของการตอบลูกค้าเก่า |
| `payments` | เงินเข้า: มัดจำ / งวด / เต็มจำนวน / ค่าต่ออายุ + สลิป | ยอดค้างรับคำนวณจากตารางนี้ลบด้วยราคาขาย |
| `expenses` | เงินออก: โดเมน โฮสต์ ธีม ปลั๊กอิน จ้างช่วง ค่าธรรมเนียม | ผูกกับงานได้ (`job_id`) หรือเป็นค่าใช้จ่ายรวมก็ได้ |
| `ad_campaigns` | แคมเปญโฆษณาบนเพจ + รหัสอ้างอิงสำหรับติดตาม | ทำให้ตอบได้ว่าแคมเปญไหนได้ลูกค้าจริง ไม่ใช่แค่ได้ยอดวิว |
| `ad_spend_daily` | ค่าโฆษณาต่อวันต่อแคมเปญ + ยอดคนทัก | ตารางนี้หน้าตาเหมือนกันหมด ไม่ว่าจะกรอกมือหรือดึงจาก API (§7) |
| `notes` | บันทึก + ไฟล์แนบ ผูกกับลูกค้าหรืองาน | ที่เก็บ "ลูกค้าขอเปลี่ยนสีเป็นเขียว" ที่ไม่ใช่แชท |
| `activity_log` | ใครเปลี่ยนอะไรเมื่อไหร่ | ย้อนดูได้ว่างานนี้ค้างมาตั้งแต่เมื่อไหร่ และเปลี่ยนสถานะตอนไหน |

### จุดที่ต้องระวังในโครงสร้าง

- **`leads` แยกจาก `jobs` โดยตั้งใจ** คนทักมา 5 คน ปิดได้ 1 คน ถ้ายุบสองตารางนี้
  เป็นตารางเดียว จะเหลือแค่ 1 แถว และ 4 แถวที่หายไปคือข้อมูลที่แพงที่สุดที่มี
- **`websites` แยกจาก `jobs`** เพราะเว็บ 1 เว็บอยู่ได้หลายปีและมีหลายงานตามมา
  (ทำครั้งแรก 990 → แก้เพิ่ม 500 → ต่ออายุปีละ 590) ทั้งหมดผูกกับเว็บเดิม
- **`job_tasks` สร้างจาก template** เก็บ template ไว้ในโค้ด/ตารางแยก
  ไม่ใช่ให้พิมพ์เช็กลิสต์ใหม่ทุกงาน งาน 990 ต้องเปิดงานได้ใน 30 วินาที
- **ห้ามเก็บรหัสผ่านลูกค้าเป็นข้อความธรรมดา** ดู §11

## §4 สถานะ — และกติกาที่ทำให้มันมีประโยชน์

### 4.1 สถานะของ Lead (ก่อนปิดการขาย)

```
ทักมา → คุยอยู่ → เสนอราคาแล้ว → รอโอนมัดจำ → ปิดการขาย ✔
                                              ↘ ไม่ตอบแล้ว ✖
                                              ↘ ไม่เอา (บันทึกเหตุผล) ✖
```

**"ไม่เอา" ต้องบังคับให้เลือกเหตุผล** — แพงไป / ทำเองได้ / ไปเจ้าอื่น / ยังไม่พร้อม /
ไม่ใช่ลูกค้ากลุ่มเรา เหตุผลนี้คือ feedback ตรงที่สุดว่าโฆษณาดึงคนผิดกลุ่มหรือราคาผิด

### 4.2 สถานะของ Job (หลังปิดการขาย)

```
รอข้อมูลลูกค้า → กำลังทำ → รอลูกค้าตรวจ → แก้ไข → รอชำระส่วนที่เหลือ → ส่งมอบแล้ว → ดูแลอยู่
```

### 4.3 กติกาที่สำคัญที่สุดในเอกสารนี้: แยก "ค้างที่เรา" กับ "ค้างที่ลูกค้า"

ทุกสถานะต้องติดธงว่ารออยู่ที่ฝั่งไหน:

| สถานะ | รออยู่ที่ | ถ้าค้างนาน แปลว่า |
|---|---|---|
| รอข้อมูลลูกค้า | **ลูกค้า** | ต้องทวง ไม่ใช่ต้องทำ |
| กำลังทำ | **เรา** | เรารับงานเกินตัว |
| รอลูกค้าตรวจ | **ลูกค้า** | ต้องทวง |
| แก้ไข | **เรา** | อาจโดนแก้ไม่จบ (§12) |
| รอชำระส่วนที่เหลือ | **ลูกค้า** | ต้องทวงเงิน — เร่งด่วนที่สุด |

หน้าแรกต้องมี 2 กล่องแยกกันเสมอ: **"ต้องทำ (n งาน)"** กับ **"ต้องทวง (n งาน)"**
มันคือคนละงานกันคนละอารมณ์ ถ้ารวมกันเป็นกองเดียวจะไม่มีอันไหนถูกทำ

### 4.4 กติกาอื่น

- เปลี่ยนสถานะทุกครั้งบันทึกลง `activity_log` พร้อมเวลา → คำนวณอายุสถานะได้
- เข้าสถานะ "ปิดการขาย" ต้องสร้าง `job` ทันทีโดยอัตโนมัติ ไม่ต้องกรอกซ้ำ
- เข้าสถานะ "ส่งมอบแล้ว" ต้องมี `website` ผูกอยู่ก่อน มิฉะนั้นเว็บนั้นจะหลุด
  จากระบบต่ออายุตลอดไป

## §5 หน้าจอ — 8 หน้า

### 5.1 หน้าแรก (วันนี้)
สิ่งเดียวที่หน้านี้ต้องทำคือบอกว่า **วันนี้ต้องทำอะไร** ไม่ใช่โชว์กราฟสวย ๆ

- แถวบน 6 ตัวเลข: งานที่ต้องทำ / ต้องทวง / เลยกำหนดส่ง / ค้างรับ (บาท) /
  กำไรเดือนนี้ / ค่าโฆษณาเดือนนี้
- รายการ **"ต้องทำวันนี้"** — งานที่รอเราอยู่ เรียงตามกำหนดส่ง
- รายการ **"ต้องทวง"** — งานที่รอลูกค้าเกิน 3 วัน พร้อมปุ่มคัดลอกข้อความทวง
- แถบ **"ใกล้หมดอายุ"** — โดเมน/โฮสต์ที่เหลือ < 30 วัน
- กราฟเส้นเล็ก ๆ 1 อัน: กำไรสุทธิ 6 เดือนย้อนหลัง

### 5.2 บอร์ดงาน (Kanban)
คอลัมน์ = สถานะใน §4.2 การ์ด 1 ใบ = 1 งาน ลากเปลี่ยนสถานะได้

บนการ์ดต้องเห็นโดยไม่ต้องเปิด: ชื่อลูกค้า · แพ็กเกจ · กำหนดส่ง ·
**ยอดค้างรับ** · จำนวนวันที่ค้างในสถานะนี้ (เกิน 7 วันเปลี่ยนเป็นสีเตือน)

### 5.3 หน้ารายละเอียดงาน — หน้าที่ใช้บ่อยที่สุด
ทุกอย่างของงานนี้ในหน้าเดียว ไม่ต้องกดไปไหนอีก:
ข้อมูลติดต่อลูกค้า (กดโทร/เปิด LINE ได้เลย) · เช็กลิสต์ · ไฟล์ที่ลูกค้าส่งมา ·
ลิงก์เว็บ + ข้อมูลโดเมน/โฮสต์ · **กล่องการเงินของงานนี้** (ราคาขาย − ต้นทุนแต่ละรายการ
− ค่าโฆษณาปันส่วน = กำไร) · บันทึก · ไทม์ไลน์

### 5.4 ลูกค้า
รายชื่อ + ค้นหา เข้าไปเห็นประวัติงานทั้งหมด มูลค่ารวมที่จ่ายมาแล้ว
เว็บที่ถืออยู่ และวันครบกำหนดต่ออายุครั้งถัดไป

### 5.5 การเงิน
- รายรับ / รายจ่าย / กำไร แยกรายเดือน (กราฟแท่ง + ตาราง)
- **ค้างรับ** — ใครค้างเท่าไหร่ กี่วันแล้ว
- ค่าใช้จ่ายแยกตามประเภท เห็นชัดว่าค่าโฆษณากินไปกี่ % ของรายรับ
- ปุ่ม Export CSV สำหรับยื่นภาษี (§11)

### 5.6 การตลาด / โฆษณา
- ค่าโฆษณารายวัน + คนทักที่ได้ + งานที่ปิดได้ ในกราฟเดียวกัน
- ตารางรายแคมเปญ: ใช้ไป / คนทัก / **ต้นทุนต่อคนทัก (CPL)** / ปิดได้ /
  **ต้นทุนต่อ 1 งาน (CAC)** / รายได้ที่เกิดจริง / ROAS
- **สัญญาณเตือนอัตโนมัติ**: CAC ของแคมเปญไหนเกินเพดานที่ตั้งไว้ ให้ขึ้นสีแดง
  พร้อมข้อความว่าแคมเปญนี้กำลังขายขาดทุน

### 5.7 ต่ออายุ
ปฏิทิน/รายการโดเมนและโฮสต์ทั้งหมดที่ดูแลอยู่ เรียงตามวันหมดอายุ
แต่ละแถว: ลูกค้า · โดเมน · หมดอายุ · ต้นทุนต่ออายุ · ราคาที่จะเก็บ · กำไร ·
สถานะ (ยังไม่แจ้ง / แจ้งแล้ว / จ่ายแล้ว / ลูกค้าไม่ต่อ)

## §6 ตัวเลขและสูตร

### 6.1 สูตรหลัก

```
กำไรขั้นต้นต่องาน = ราคาขาย − ต้นทุนตรงของงาน
กำไรสุทธิต่องาน   = กำไรขั้นต้น − ค่าโฆษณาปันส่วน

ค่าโฆษณาปันส่วน   = ค่าโฆษณาทั้งเดือน ÷ จำนวนงานที่ปิดได้ในเดือนนั้น
                   (= CAC ซึ่งเป็นตัวเดียวกัน)

CPL  = ค่าโฆษณา ÷ จำนวนคนที่ทักมา
CAC  = ค่าโฆษณา ÷ จำนวนงานที่ปิดได้
อัตราปิดการขาย = งานที่ปิดได้ ÷ คนที่ทักมา
ROAS = รายได้ที่เกิดจากแคมเปญ ÷ ค่าโฆษณาของแคมเปญนั้น
กำไรต่อชั่วโมง = กำไรสุทธิ ÷ ชั่วโมงที่ใช้จริง
```

### 6.2 ตัวอย่างที่ราคา 990 — ใส่ตัวเลขจริงของคุณแทน

สมมติ: ค่าโฆษณา 3,000/เดือน, มีคนทัก 100 คน, ปิดได้ 20 งาน

| รายการ | บาท |
|---|---:|
| ราคาขาย | 990 |
| − ธีม/ปลั๊กอิน/รูปเฉลี่ย | −60 |
| − ค่าธรรมเนียมรับเงิน | −10 |
| = **กำไรขั้นต้น** | **920** |
| − ค่าโฆษณาปันส่วน (3,000 ÷ 20) | −150 |
| = **กำไรสุทธิ** | **770** |

CPL = 3,000 ÷ 100 = **30 บาท** · CAC = 3,000 ÷ 20 = **150 บาท** ·
อัตราปิด = **20%** · ถ้าใช้เวลา 5 ชม./งาน = **154 บาท/ชม.**

### 6.3 เส้นตายที่ระบบต้องเฝ้าให้

ตัวเลขข้างบนดูดี แต่มันเปราะกว่าที่คิด ถ้า CPL ขึ้นจาก 30 เป็น 60 บาท
(เกิดขึ้นง่ายมากเวลามีคนยิงแข่ง) CAC จะเป็น 300 และกำไรเหลือ 620 บาท
ถ้าอัตราปิดตกจาก 20% เหลือ 10% พร้อมกัน CAC จะเป็น 600 และเหลือกำไร 320 บาท —
คือ **64 บาท/ชม.**

**ให้ระบบตั้งเพดาน CAC ไว้ที่ตัวเลขหนึ่ง แล้วเตือนเมื่อทะลุ** ค่าตั้งต้นที่แนะนำ
คือ 300 บาท (ประมาณ 1 ใน 3 ของกำไรขั้นต้น) เพราะเกินจากนั้น รายได้ต่อชั่วโมง
จะต่ำกว่าการไปรับงานอื่น นี่คือฟีเจอร์ที่คุ้มค่าที่สุดในระบบทั้งหมด

### 6.4 ตัวเลขที่จะเปลี่ยนธุรกิจนี้จริง ๆ: รายได้ต่ออายุ

งานใหม่ 1 งาน = กำไร ~770 บาท และต้องจ่ายค่าโฆษณาเพื่อให้ได้มา
ค่าต่ออายุ 1 เว็บ = **กำไรเกือบเต็ม และไม่ต้องจ่ายค่าโฆษณาเลย**

ถ้าเก็บค่าดูแล+ต่ออายุปีละ 590 บาท และต้นทุนโดเมนจริง 450 บาท กำไร 140 บาท/เว็บ —
ยังน้อย **ราคาต่ออายุคือสิ่งที่ควรพิจารณาขึ้นก่อนราคางานใหม่** เช่น 990/ปี
(ดูแล + ต่ออายุ + แก้ข้อความให้ปีละ 2 ครั้ง) จะได้กำไร ~540/เว็บ/ปี
ที่ 50 เว็บ = **27,000 บาท/ปี ที่ไม่ต้องยิงโฆษณาเพื่อให้ได้มา**

ระบบต้องทำให้ตัวเลขนี้เห็นชัดบนหน้าแรก มิฉะนั้นมันจะถูกลืมทุกปี

## §7 เชื่อมต่อกับเพจที่ยิงโฆษณา

เป้าหมายคือ 2 อย่าง: **ดึงค่าโฆษณาเข้ามาเป็นต้นทุนอัตโนมัติ** และ
**รู้ว่าลูกค้าคนนี้มาจากแคมเปญไหน**

### 7.1 ทำเป็น 2 ระดับ และออกแบบให้เปลี่ยนระดับได้โดยไม่แก้หน้าจอ

ตาราง `ad_spend_daily` มีหน้าตาเดียว ไม่ว่าข้อมูลจะมาจากทางไหน
ต่างกันแค่คอลัมน์ `source` (`manual` / `csv` / `api`)

**ระดับ 1 — กรอก/นำเข้าเอง (เริ่มด้วยอันนี้)**
- ที่ Meta Ads Manager กดส่งออกรายงานเป็น CSV แล้วอัปโหลดเข้าระบบ สัปดาห์ละครั้ง
- ใช้เวลาจริงประมาณ 5 นาที/สัปดาห์
- ได้ตัวเลขครบทุกอย่างใน §6 ทันที **โดยไม่ต้องรออนุมัติอะไรจาก Meta เลย**

**ระดับ 2 — ต่อ API อัตโนมัติ (ทำทีหลัง)**
- Meta Marketing API endpoint `act_<ad_account_id>/insights`
  ดึง `spend`, `impressions`, `clicks`, `actions` รายวันรายแคมเปญ
- ต้องมี: Meta app, System User token, สิทธิ์ `ads_read`,
  และบัญชีธุรกิจที่ผ่าน Business verification
- งานตรงนี้ไม่ยาก แต่ **ขั้นตอนอนุมัติของ Meta กินเวลาเป็นสัปดาห์** จึงไม่ควร
  เอามาขวางการเริ่มใช้ระบบ

### 7.2 การรู้ว่าลูกค้ามาจากแคมเปญไหน

นี่คือส่วนที่ยากกว่าค่าโฆษณา และมีทางลัดที่ได้ผลจริง:

**วิธีที่แนะนำ — ใส่รหัสอ้างอิงในลิงก์โฆษณา**
ใช้ลิงก์ `m.me/<ชื่อเพจ>?ref=camp_a1` เป็นปลายทางของโฆษณาแต่ละตัว
เมื่อคนกดทัก Messenger จะส่งค่า `ref` มาด้วย ทำให้ผูกคนทัก → แคมเปญ ได้ตรง ๆ
(ต้องต่อ webhook ของเพจ ซึ่งต้องขอสิทธิ์ `pages_messaging` และผ่าน App Review)

**วิธีที่ใช้ได้ตั้งแต่วันแรกโดยไม่ต้องขออะไร**
เวลาบันทึก lead ให้เลือกแคมเปญจาก dropdown เอง 1 คลิก
ตอนมี 5–10 คนทักต่อวัน นี่เร็วกว่าการรอ App Review หลายสัปดาห์
และให้ข้อมูลคุณภาพเท่ากัน

**ถ้าใช้ Lead Ads (ฟอร์มในเฟซบุ๊ก)** จะง่ายกว่ามาก — ดาวน์โหลด CSV ได้ตรง ๆ
หรือต่อ webhook `leadgen` (ต้องสิทธิ์ `leads_retrieval`) และ CSV มี campaign id ติดมาด้วยแล้ว

### 7.3 ข้อควรรู้

- ตัวเลข "ผลลัพธ์" ใน Ads Manager กับจำนวนคนที่ทักจริงมักไม่ตรงกัน
  **ให้ยึดตัวเลขที่บันทึกในระบบเราเป็นหลัก** และใช้ตัวเลขของ Meta เป็นตัวอ้างอิงเฉย ๆ
- ค่าโฆษณาที่ Meta รายงาน ยังไม่รวม VAT ในบางบัญชี ตรวจกับใบเสร็จจริงเดือนละครั้ง
- อย่าเก็บ access token ไว้ในโค้ด ใช้ตัวแปรสภาพแวดล้อมเท่านั้น

## §11 ความปลอดภัยและข้อมูลส่วนบุคคล

**รหัสผ่านของลูกค้า (WordPress admin, cPanel, ผู้ให้บริการโดเมน)**
อย่าเก็บเป็นข้อความธรรมดาในฐานข้อมูล ทางเลือกเรียงตามที่แนะนำ:
1. **ไม่เก็บเลย** — เก็บแค่ "อยู่ใน Bitwarden ชื่อรายการ X" ปลอดภัยที่สุดและฟรี
2. ถ้าจำเป็นต้องเก็บจริง ใช้ `pgcrypto` เข้ารหัสด้วยคีย์ที่อยู่ใน env
   ไม่ใช่ในฐานข้อมูล และจำกัดว่าใครถอดได้

**PDPA** — ชื่อ เบอร์ ที่อยู่ ลิงก์เฟซบุ๊กของลูกค้า คือข้อมูลส่วนบุคคลตามกฎหมาย
เก็บเท่าที่จำเป็น มีปุ่มลบลูกค้าออกจากระบบได้จริง และอย่าส่งข้อมูลนี้ออกไป
บริการภายนอกโดยไม่จำเป็น

**สำรองข้อมูล** — Supabase สำรองให้อยู่แล้ว แต่ให้ตั้ง export ฐานข้อมูลออกมา
เก็บนอกระบบเดือนละครั้งด้วย ระบบนี้จะกลายเป็นที่เดียวที่มีข้อมูลลูกค้าทั้งหมด

**ภาษี** — บันทึกรายรับให้ครบตั้งแต่วันแรก รายได้จากรับจ้างทำเว็บเป็นเงินได้
ที่ต้องยื่น การมีข้อมูลครบทำให้เลือกหักค่าใช้จ่ายตามจริงได้ ซึ่งมักได้เปรียบกว่า
หักเหมาเมื่อมีค่าโฆษณาสูง ให้หน้า §5.5 ส่งออก CSV ที่มีวันที่/ประเภท/จำนวน
เตรียมไว้เลย

## §12 สิ่งที่คนมักลืม

1. **ไม่ปันส่วนค่าโฆษณา** → เห็นกำไรเกินจริงทุกเดือน จนวันที่เงินไม่พอถึงรู้ตัว
2. **ไม่บันทึกคนที่ไม่ซื้อ** → ไม่มีอัตราปิดการขาย ปรับโฆษณาแบบเดา ๆ ตลอดไป
3. **ไม่จำกัดรอบแก้** → งาน 990 ที่แก้ 8 รอบคืองานที่ขาดทุน ให้มีช่อง
   "รอบแก้ที่ใช้ไป / ที่รวมในแพ็ก" บนการ์ดงาน และเตือนเมื่อเกิน
4. **ไม่บันทึกเวลาที่ใช้** → ไม่รู้ว่าควรขึ้นราคาเมื่อไหร่ ไม่ต้องจับเวลาละเอียด
   แค่ประมาณเป็นชั่วโมงตอนปิดงานก็พอ
5. **ลืมว่าโดเมนเป็นภาระผูกพัน** → เว็บดับพร้อมกัน 5 เว็บในเดือนเดียวเกิดขึ้นได้จริง
6. **เก็บรหัสผ่านลูกค้าในแชท** → ทั้งหาไม่เจอและไม่ปลอดภัย
7. **ทำระบบใหญ่เกินก่อนใช้จริง** → เฟส 1 ต้องเสร็จใน 3 วัน ถ้าเกินกว่านั้น
   แปลว่ากำลังสร้างของที่ไม่ได้ใช้
